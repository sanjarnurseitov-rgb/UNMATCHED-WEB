# Unmatched Match Tracker — аналитический дашборд

Веб-приложение для анализа матчей по настольной игре **Unmatched**.
База данных — ваша существующая Google Таблица; приложение **только читает**
её и строит дашборд с глубокой статистикой: тир-лист героев, матрица
матчапов, синергии и анти-синергии, немезиды, баланс первого хода и полей
боя.

**Приложение ничего не записывает в таблицу.** Ни страницы записи матча, ни
API для записи, ни кнопок «добавить» — только чтение и аналитика.

Идентификатор таблицы уже прописан по умолчанию:
`15IJy050me3WkkI2vYf10tMhCFCKF0dglRY_HaBF96vQ`

## 1. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Framework | **Next.js 15 (App Router) + TypeScript** | Server Components отдают статистику сразу в HTML — дашборд открывается мгновенно. Отдельный бэкенд не нужен. |
| UI | **React 19 + Tailwind CSS v4** | Тёмная «игровая» тема собирается из CSS-переменных, без UI-кита. |
| Графики | **Recharts 3** | Декларативные SVG-графики, хорошо дружат с React 19 и SSR. |
| Sheets | **googleapis** (официальный клиент) + публичный CSV-экспорт | Чтение только на сервере. Работает и без сервисного аккаунта. |
| Валидация | **Zod** | Схемы запросов/ответа на границе приложения. |
| Хостинг | **Vercel** | Бесплатный тариф, env-переменные, автодеплой из Git. |

**Почему не low-code (Apps Script / Airtable / Notion):** таблица сложилась
под конкретную форму ответов, а расчёт винрейтов, матчапов и синергий — это
агрегация по сотням строк с ветвлением по режиму. Apps Script справился бы с
формулами, но интерактивный дашборд с drill-down’ом в нём пришлось бы
собирать вручную.

## 4. Структура таблицы

### Вкладка `Ответы на форму (3)` — история матчей

Одна широкая строка на матч. 1 vs 1 заполняет колонки C..J, 2 vs 2 —
K..V.

| Кол. | Значение | | Кол. | Значение |
|---|---|---|---|---|
| A | Отметка времени | | L | Команда 1 Игрок 1 |
| B | Режим игры | | M | Команда 1 Герой 1 |
| C | Игрок 1 | | N | Команда 1 Игрок 2 |
| D | Герой 1 | | O | Команда 1 Герой 2 |
| E | Игрок 2 | | P | Команда 2 Игрок 3 |
| F | Герой 2 | | Q | Команда 2 Герой 3 |
| **G** | **Поле 1 vs 1** | | R | Команда 2 Игрок 4 |
| H | Победитель 1 vs 1 | | S | Команда 2 Герой 4 |
| I | Комментарий 1 vs 1 | | T | Победитель |
| J | Локация матча 1 vs 1 | | U | Комментарий |
| **K** | **Поле 2 vs 2** | | V | Локация матча |

Победитель кодируется **позицией**, а не именем: `Игрок 1` / `Игрок 2` в 1 vs 1
и `Команда 1` / `Команда 2` в 2 vs 2.

### Вкладка `PlayerList` — справочники

| Кол. | Значение |
|---|---|
| A | полный список героев |
| C | СПИСОК ИГРОКОВ |
| D | герои для анкеты |
| F | фан персы игранные |
| I | Поля 2 на 2 |
| J | Поля 1 vs 1 |

Справочник ведётся вручную и **отстаёт от реальности**: в нём 18 игроков и
78 героев, а в истории матчей встречаются 63 игрока и 126 героев. Поэтому
выпадающие списки строятся как **объединение** справочника и истории —
иначе часть игроков была бы недоступна.

### Вкладка `IMAGES` — картинки

Колонки: **Имя | Тип | URL**, где `Тип` — `hero`, `player` или `Map`.

Вкладка может содержать **несколько блоков колонок рядом** (в текущей
таблице их два: первый — герои и игроки с картинками, второй — поля боя).
Блоки определяются по строке заголовков, а не по жёстко заданным номерам
колонок, поэтому в любой блок можно в любой момент добавить колонку `URL`.

```
Имя       | Тип   | URL                    | Имя                      | Тип  | URL
Алиса     | hero  | https://…/алиса.webp  | Yukon(Робин vs Бигфут)   | Map  | https://…/yukon.webp
```

Парсер (`indexImages` в `src/lib/data.ts`) умеет:

- находить блоки по заголовкам `Имя/Name`, `Тип/Type`, `URL/Ссылка/Link`;
- понимать русские значения типа (`Герой`, `Игрок`, `Поле`);
- работать без строки заголовков (тогда: A = имя, B = тип, C = URL);
- принимать и `Map`, и `map`, и `Поле` как тип поля.

Ключи героев и игроков — нормализованные (`identityKey`), ключи полей —
`mapKey`, поэтому `Marmoreal(Том 1)` из таблицы и `Marmoreal(Том1)` из
справочника — один и тот же ключ.

> **Как добавить картинку поля боя.** Впишите URL в колонку `URL` блока с
> полями (или добавьте эту колонку рядом с ним) — и «Топ-3 поля» на
> дашборде сразу покажет реальную картинку. Пока URL нет, поле рисуется
> красивым сгенерированным градиентом (см. `MapArt` в `src/components/ui.tsx`).

### Вкладки `Матчи 1 на 1` и `Матчи 2 на 2` — контрольная копия истории

Это ручная разбивка той же истории по режимам:

```
Матчи 1 на 1:  Дата | Режим | Игрок 1 | Герой 1 | Игрок 2 | Герой 2 | Карта | Победитель | Комментарий
Матчи 2 на 2:  Дата | Режим | Карта | Команда 1 (Игрок 1 | Герой 1 | Игрок 2 | Герой 2) |
                Команда 2 (Игрок 1 | Герой 1 | Игрок 2 | Герой 2) | Победитель
```

Приложение **не берёт** из них строки — источником матчей остаётся
`Ответы на форму (3)`. Они читаются как **независимая копия** для
сверки: приложение сравнивает свои счётчики героев и игроков с этими
листами и показывает результат в панели «Качество данных» (см.
[Проверка агрегации](#проверка-агрегации)). Если в историю попадёт
строка, которая не доехала до формы ответов, приложение это покажет,
а не промолчит.

## 5. Архитектура данных

```
sheets.ts  ──►  parse.ts  ──►  normalize.ts  ──►  stats.ts  ──►  AppData  ──►  UI
(сырые)       (Match[])      (ключи, даты)      (агрегаты)     (снимок)
```

| Файл | Ответственность |
|---|---|
| `src/lib/sheets.ts` | Чтение таблицы: три провайдера (`api`, `public`, `snapshot`) с кэшем на 20 секунд |
| `src/lib/parse.ts` | Строка таблицы → нормализованный `Match`; разбор сводных листов «Матчи 1 на 1» / «Матчи 2 на 2» |
| `src/lib/normalize.ts` | Нормализация имён (`identityKey`), полей (`mapKey`), заглушки, чёрный список героев, разбор дат |
| `src/lib/stats.ts` | Вся агрегация: лидерборды, матчапы, синергии, тир-лист, баланс, проверка сходимости |
| `src/lib/results.ts` | Кто выиграл матч: общие для сервера и браузера правила определения победителя |
| `src/lib/data.ts` | Сборка `AppData`: загрузка → разбор → справочники → статистика |
| `src/lib/types.ts` | Типы домена |

Движок статистики — **чистая функция** от `(matches, reference)`. Поэтому
переключатель «Скрыть фан-героев» пересчитывает всё прямо в браузере, без
обращения к серверу.

### Провайдеры чтения

| Провайдер | Когда | Как читает |
|---|---|---|
| `api` | есть ключи сервисного аккаунта | `googleapis` → `values.get` |
| `public` | по умолчанию | публичный CSV-экспорт по `gid` |
| `snapshot` | `DATA_SOURCE=snapshot` | `src/lib/snapshot.json` (офлайн) |

Вкладка `IMAGES` в публичном режиме читается по **имени вкладки** через
gviz-экспорт (`…/gviz/tq?tqx=out:csv&sheet=IMAGES&range=A1:Z400`) — потому
что её `gid` неизвестен приложению. Явный широкий диапазон гарантирует, что
придут **все** колонки всех блоков (иначе экспорт обрезает хвостовой блок с
картинками полей). Если `SHEETS_TAB_IMAGES_GID` задан, используется обычный
экспорт по `gid`.

Офлайн-снимок (`src/lib/snapshot.json`) обновляется скриптом:

```bash
node scripts/refresh-snapshot.mjs
```

Он заново скачивает `Ответы на форму (3)`, `PlayerList`, `IMAGES` и оба
сводных листа — вместе со строкой заголовков (без неё первая строка молча
теряется).

## 6. Статистика: что и как считается

### Победа игрока определяется по номеру места

```ts
function winningSeats(match: Match): Set<number> {
  const seats = new Set<number>();
  if (match.mode === '1v1') {
    if (match.winner === 'p1') seats.add(0);
    else if (match.winner === 'p2') seats.add(1);
  } else {
    if (match.winner === 't1') { seats.add(0); seats.add(1); }
    else if (match.winner === 't2') { seats.add(2); seats.add(3); }
  }
  return seats;
}
```

### Сценарий «1 игрок против 2 игроков» (2 vs 2)

Один игрок может вести **сразу двух героев** против двух соперников. В
таблице это один и тот же игрок в обоих местах одной команды. Такие строки
**не считаются ошибкой** — это полноценные матчи.

| Что | Как считается |
|---|---|
| Матч игрока | **один раз**, а не два |
| Победа/поражение | результат команды, в которой он играл |
| Герои | **оба** героя засчитываются за этого игрока |
| Пара игроков | не считается синергией — игрок не партнёр самому себе |
| Пара героев | считается синергией — эти два героя играли вместе |

### Тир-лист героев

Тир присваивается по винрейту, пороги **абсолютные** (чтобы список не
пересчитывался при добавлении нового героя):

| Тир | Винрейт |
|---|---|
| S | ≥ 60 % |
| A | ≥ 55 % |
| B | ≥ 50 % |
| C | ≥ 45 % |
| D | < 45 % |

В тир-лист попадают только герои с **5+ матчами** (`MIN_GAMES_FOR_TIER`).

### Пик рейт

`пик рейт = матчей с героем ÷ все матчи`. Показывает, насколько часто
героя вообще берут.

### Баланс первого хода

Отдельной колонки «кто ходил первым» в таблице нет, поэтому **Игрок 1
(1 vs 1) и Команда 1 (2 vs 2) считаются ходившими первыми**. Считается
доля матчей, выигранных тем, кто ходил первым.

### Немезиды по режимам

Дуэльный матчап и командная игра — разные вещи, поэтому немезиды
считаются **отдельно для каждого режима**:

- **1 vs 1** — каждый герой встретился с соперником один на один;
- **2 vs 2** — каждый герой одной команды считается соперником каждого
  героя другой команды (за матч — четыре пары «свой — чужой»).

В модалке героя показываются четыре блока: «Худший враг · 1 vs 1»,
«Худший враг · 2 vs 2», «Лучшая жертва · 1 vs 1», «Лучшая жертва · 2 vs 2».
На странице «Матчапы» есть таблица немезидов для 1 vs 1 и отдельная — для
2 vs 2.

### Матчапы 1 vs 1 и немезиды

Для каждой пары героев, встречавшихся в 1 vs 1, считаются матчи и победы
каждого. Из этих данных:

- **Матрица матчапов** — винрейт героя по строке против героя по столбцу;
- **Худший враг (nemesis)** — соперник с **самым низким** винрейтом против
  данного героя, то есть тот, кто его обыгрывает чаще всего;
- **Лучшая жертва (best victim)** — соперник с **самым высоким** винрейтом
  против данного героя, то есть тот, кого герой обыгрывает чаще всего.

Правила отбора:

1. В пул попадают **только соперники, с которыми герой сыграл ≥ 2 раза**
   (`MIN_GAMES_FOR_NEMESIS = 2`). Одна игра даёт бессмысленные 100 % / 0 %,
   поэтому такие соперники не могут быть ни немезисом, ни жертвой.
2. Оба слота выбираются **из одного и того же пула**: nemesis — с
   минимальным винрейтом, best victim — с максимальным.
3. Если пул содержит больше одного соперника, nemesis и best victim —
   это **всегда разные персонажи**. При равенстве винрейтов приоритет у
   соперника с большей выборкой; если из-за равенства оба слота указали бы
   на одного и того же героя, второй слот занимает следующий соперник.
4. Если квалифицировался только **один** соперник, приложение не
   дублирует его в двух карточках: показывается одна карточка «Единственный
   соперник с достаточной выборкой» с пояснением. В таблице немезидов
   такой соперник показан один раз — в той колонке, которая соответствует
   его результату.
5. Если соперников с 2+ матчами нет, оба слота честно остаются пустыми
   («Нет соперников с достаточной выборкой»), а полный список соперников с
   их выборками всё равно доступен в модалке героя.

### Проверка агрегации

Приложение не доверяет своим же счётчикам — оно их **проверяет** при каждой
загрузке и показывает результат в панели «Качество данных» на дашборде:

| Проверка | Что делает |
|---|---|
| **Сходимость сумм** | Для каждого героя `games === games1v1 + games2v2`. Любое нарушение попадает в отчёт. |
| **Сверка со сводными листами** | Счётчики героев и игроков сравниваются с независимой копией истории из листов «Матчи 1 на 1» и «Матчи 2 на 2». |

Сверка считает только валидные строки и применяет те же фильтры, что и
движок (заглушки, чёрный список героев), а игрок считается **один раз на
матч**, даже если он занимал два места (двойной контроль).

> Текущее состояние: 2830 вхождений героев и 2756 игровых мест — расхождений
> нет, все 126 героев сходятся.

Отчёт лежит в `stats.consistency` (`ConsistencyReport` в
`src/lib/types.ts`) и переживает переключатель «Скрыть фан-героев»: он
описывает исходные данные, а не фильтр.

### Синергии и анти-синергии

Пара героев — это те, кто сидел в одной команде в 2 vs 2. Пара получает
победу, если её команда выиграла. Порог отсечения — **3 матча**
(`MIN_GAMES_FOR_SYNERGY`), иначе лидерборд выигрывают пары с одним матчем и
100 % винрейтом.

- **Лучшие синергии** — пары с самым высоким винрейтом;
- **Анти-синергии** — пары с самым низким винрейтом.

### Пустое поле боя

Матч без выбранного поля **не попадает ни в один рейтинг полей** — ни
отдельной строкой, ни в график популярности. Он учитывается в общей
статистике, у игроков, у героев и на графике активности, но количество
таких матчей считается отдельно (`stats.totals.unmappedMatches`) и
показывается информационной панелью «Без поля боя».

### Нормализация названий полей

Ключ группировки (`mapKey`) игнорирует регистр, пробелы, дефисы, апострофы и
притяжательную форму:

```ts
export function mapKey(value: string): string {
  return canonicalName(value)
    .toLowerCase()
    .replace(/ё/g, 'е')
    .replace(/\b['‘’]s\b/g, '')   // "Santa's Workshop" -> "Santa Workshop"
    .replace(/[-–—_/]/g, '')
    .replace(/['‘’"`«»]/g, '')
    .replace(/\s+/g, '');
}
```

Так `Marmoreal(Том 1)` и `Marmoreal(Том1)`, а также `Santa's Workshop(Том 3)`
и `Santa workshop(Том 3)` — это **одно** поле.

### Модальное окно игрока

Аватар игрока **кликабелен глобально** — в таблицах игроков и героев,
синергиях, очных противостояниях, истории матчей, «Топ-3 полей» и на
странице «Поля боя». Клик открывает модалку с профилем игрока:

- общие числа (винрейт, победы, поражения, число любимых героев) и чипы
  (число матчей, винрейт, счётчик двойного контроля);
- полоса винрейта и разбивка **1 vs 1 / 2 vs 2**;
- **«Последние 10 матчей»** — новейшие сверху, с героями игрока,
  соперниками, полем боя, датой и результатом;
- **«Любимые герои»** (топ-5 с винрейтом) и **«Любимые поля»** (топ-5).

Блок «Последние матчей» стоит **перед** любимыми героями и полями — так
видно, что происходило с игроком, и только потом его предпочтения.

Список последних матчей считается прямо в браузере из уже загруженной
истории (`recentMatchesFor` в `src/components/PlayerModal.tsx`), поэтому
лишние данные на сервер не передаются.

### Модальное окно героя

Аватар героя **кликабелен глобально** — в тир-листе, таблице героев,
синергиях, истории матчей и на странице «Поля боя». Клик открывает
**единственную** модалку героя в приложении (собственной drill-down
модалки у таблицы лидеров больше нет — клик по строке открывает ту же
глобальную модалку). В ней:

- тир и общие числа (винрейт, победы, поражения, пик рейт);
- разбивка 1 vs 1 / 2 vs 2;
- **худший враг** и **лучшая жертва** — отдельными блоками для 1 vs 1 и
  2 vs 2 (см. «Немезиды по режимам»);
- **любимое поле**;
- **лучший союзник** (и худший);
- сводная таблица всех соперников.

Модалка выносится в `document.body` через портал и центрируется
во вьюпорте.

## 8. Изображения

### Как аватар находит свою картинку

`<HeroAvatar>` и `<PlayerAvatar>` **сами** ищут картинку героя или игрока в
данных вкладки `IMAGES` (по нормализованному имени). Явно передавать `image`
не нужно — и нельзя забыть: именно из-за забытых `image` часть блоков
показывала цветные буквы вместо портретов.

Если у героя или игрока в таблице `IMAGES` нет строки с типом `hero` /
`player` и URL, аватар покажет монограмму — это осознанный запасной вариант
(например, у игроков картинок в таблице сейчас нет вообще).

Все картинки в приложении — портреты героев, игроков и плитки полей —
рендерятся обычным тегом `<img>`, **не** `next/image` и **не** через
`background-image`: это снимает ограничения на домены
(`images.remotePatterns` не нужен, ссылки на Google Drive, imgur, GitHub и
любые CDN работают сразу) и оставляет у картинок нормальный `alt`.
Плитка поля (`MapArt`) кладёт `<img>` внутрь и накрывает её слоем
затемнения, а если картинки нет — рисует детерминированный градиент.

```tsx
<img
  src={image}
  alt={name}
  onError={() => setFailed(true)}
  style={{ width: size, height: size }}
  className={`${rounded} shrink-0 object-cover ring-1 ring-ink-600`}
/>
```

Если картинки нет или она не загрузилась, рисуется детерминированный
цветной монограм, посчитанный из имени — дашборд никогда не выглядит
«битым».

### Где взять сами картинки

| Способ | Как | Нюанс |
|---|---|---|
| **Google Drive** | загрузить файл → «Поделиться» → «Вставить ссылку» → ID вида `1AbC…` | Нужен **прямой** URL: `https://drive.google.com/uc?export=view&id=<ID>`. Обычная ссылка на просмотр отдаст HTML. |
| **GitHub / imgur** | загрузить файл, скопировать raw-ссылку | Самый простой вариант, домен не заблокирован. |
| **Яндекс.Диск** | публичная ссылка вида `https://disk.yandex.ru/i/<ID>/` | Подходит как прямой URL. |
| **img.unmatched.club** | `https://img.unmatched.club/heroes/avatars/<id>.webp` | Готовые портреты героев, уже лежат в таблице. |

**Альтернативы и почему они хуже:**

- **Base64 в ячейке** — не делайте. Ячейка в Google Sheets ограничена
  50 000 символами, а картинка в base64 — это десятки килобайт.
- **Загрузка файлов через форму** — требует отдельного хранилища (S3, Cloud
  Storage, Cloudinary) и отдельного API-ключа. Прямой URL из Drive решает
  задачу без лишней инфраструктуры.

### Почему модальное окно съезжало

`position: fixed` позиционируется относительно вьюпорта **только если у
предка нет трансформации**. Панели приложения анимируются классом
`.animate-fade-up`, и анимация с `animation-fill-mode: both` оставляет
`transform: translateY(0)` — такой transform делает панель containing block
для `position: fixed`, и модалка центрировалась по панели (то есть по середине
всей страницы, а не экрана).

Исправлено двумя способами сразу:

1. Модалка выносится в `document.body` через `createPortal` — предок с
   трансформацией больше не участвует в позиционировании.
2. `animation-fill-mode` заменён на `backwards`, чтобы трансформация не
   задерживалась после окончания анимации.
3. У самой модалки **свои keyframes** (`modal-fade-up`): общие `fade-up`
   анимировали `transform` и на время анимации затирали центрирующий
   `translate(-50%, -50%)` — панель прыгала в середину вьюпорта и
   «съезжала» вниз-вправо. Собственные keyframes сохраняют смещение, поэтому
   панель центрирована в любой момент анимации.

```css
.modal-overlay { position: fixed; inset: 0; z-index: 60; }
.modal-panel {
  position: fixed; top: 50%; left: 50%;
  transform: translate(-50%, -50%); z-index: 61;
}
```
